02 / ROWS BECOME COLUMNS

Same rows.
A different arrangement.

Parquet stores values column by column, not as a sequence of complete records.

First, take a batch of rows: a row group. Within that group, each column has its own column chunk.

Our one row group has 12 rows and 7 column chunks. Reading revenue needn’t decode region or product values.

The revenue chunk is split into pages. Here, each holds four values. Order 8 lives in the third page, P18.

A stored page has a Parquet header and encoded, usually compressed data. We’re showing its decoded values so you can see inside.

04 / VPF SEPARATES THE MAP FROM THE BYTES

The map can change.
The pages don’t.

A snapshot is a saved view of the table. Its metadata selects visible segments: here, one row group, its chunks, and their page IDs.

VPF puts that metadata and the immutable Parquet page bytes inside one SQLite file.

It uses SQLite as its transactional container. It does not turn your orders into a conventional SQLite row table.

06 / FOLLOW THE CHANGE INWARD

A new page.
Not a new table.

VPF decodes the affected revenue page, changes the value, and encodes a new page, P22. The old P18 is untouched.

New chunk and row-group metadata point to P22. Snapshot 2 becomes current in the same SQLite transaction.

1 data page written. 20 reused. That excludes metadata, page reads, and SQLite’s own WAL/page writes; it is not a disk-I/O count.

07 / THE PAST STILL HAS ITS OWN MAP

Two versions.
Mostly the same pieces.

Snapshot 1 still points to P18. Snapshot 2 points to P22. Both reference the same 20 unchanged pages.

Choose a snapshot to watch the table and its page reference change together.

Nothing is “undone” on disk. A read simply follows an older map. VPF currently keeps old pages: there is no garbage collection.

08 / GIVE THE READER A FILE

Parquet on the outside.
References underneath.

A reader expects an ordinary Parquet byte stream. VPF assigns virtual offsets to the selected pages and supplies a footer describing the schema and locations.

A range read maps those offsets back to stored bytes. No full export is required.

Magic bytes and the generated footer are in memory. Stored data pages come from SQLite blobs. The strip shows the revenue extents; 18 other data pages are collapsed.

09 / BACK TO ONE ANSWER

Find the pieces.
Read the value.

SELECT revenue_cents
FROM orders WHERE id = 8;

The ID pages have bounds 0–3, 4–7, 8–11. The first two ranges cannot contain 8, so they can be skipped.

Read the candidate ID page and the corresponding revenue page. DuckDB checks id = 8 exactly and returns 12,345.

This is the DuckDB extension’s supported filter-pruning path. Bounds select candidates, not an exact row index. Generic Parquet readers make their own pruning choices.

A LITTLE DEEPER, WHEN YOU’RE READY.

The practical details.

What happens to appends, deletes, and schema changes?

Small appends can stay in compact columnar batches; reads synthesize and cache Parquet row groups. Flush stores their pages. Auto append directly encodes batches of at least 65,536 rows.

Deletes rewrite touched pages across columns to preserve row alignment. Rename, reorder, and drop use stable column IDs and change metadata rather than rewriting values.

When is the virtual layout prepared?

Lazy, the default: resolve it on demand. Lazy appends avoid loading the existing row groups, page metadata, and buffered payloads. The C API caches one resolved snapshot per handle.

Eager: persist each new snapshot’s footer and offset mapping in the write transaction. Reads can reuse them after reopen, at the cost of more write CPU and storage. Buffered snapshots also persist synthesized Parquet pages. Either mode reads a persisted layout if one exists; changing modes does not backfill history.

How can I query the actual file?

DuckDB’s VPF storage extension uses the Arrow C API. DuckDB plans and executes the SQL; VPF supplies data, projection, and conservative statistics-based pruning. Supported AND filters intersect candidate ranges; OR filters union them. Unsupported OR branches prevent pruning that disjunction.

LOAD 'vpf.duckdb_extension';
ATTACH 'orders.vpf' AS data (TYPE vpf);
SELECT revenue_cents FROM data.orders WHERE id = 8;

The example assumes the extension is already built for your DuckDB version and orders.vpf exists. The unsigned extension needs unsigned-extension loading enabled. See the build and loading instructions.

Other paths are the Rust ChunkReader API, HTTP byte ranges, a read-only FUSE mount, or exporting a standalone Parquet file. With HTTP, resolve latest once and pin the snapshot URL for the whole query.

What does this design cost?

Old snapshots and pages take space; VPF has no compaction or garbage collection. Rewritten pages use PLAIN encoding. Bloom filters are not emitted. SQLite WAL permits multiple readers and one writer, not simultaneous writers.

VPF is not universally faster than SQLite or native Parquet. Workload, metadata policy, page layout, and history all matter. The repository’s measured benchmarks include methods, caveats, and raw reports.

Are these real bytes and production data?

The values exactly follow the deterministic synthetic orders generator in benches/analytical.py. Our table contains IDs 0–11 and seven columns: id, region, product_id, day, quantity, revenue_cents, and discount_cents.

Page IDs, four-row boundaries, B-tree blocks, and byte offsets are teaching illustrations, not a measured physical file. Displayed values are decoded; actual Parquet bodies are encoded and usually compressed. This runs only in your browser and does not execute the Rust engine or submit your data.
